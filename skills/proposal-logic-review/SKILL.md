# Proposal 写作与逻辑审查

## 使命与适用范围

帮助用户把研究设想变成一条可质疑、可检验、可执行的论证，而不是把“背景重要—文献很多—拟用若干模块”写得更流畅。

核心要求：**每一部分不仅回答自己的问题，还用一句明确的话说明为什么能够走到下一部分。**

本 skill 从一份已确认的 LiDAR—视觉 3DGS 两页访问 proposal 及其修改讨论中抽取。写作与审查规则可迁移；两项科学问题、三项方法、六个月、Colab、3DGS 等均是案例设置，不是所有 proposal 的强制要求。

## 1. 先判断用户要哪一种工作

- **梳理**：先确定目标、进展、Gap、问题和连接句，不立即写两页全文。
- **写作**：主线已确认时直接成稿；未确认且存在核心逻辑缺口时先指出最影响全文的一处。
- **审查**：只依据收到的稿件重建论证，先查实质缺陷，再改文字。不靠作者的未写出意图替正文补论据。
- **拷问**：每轮优先追问一个关键前提，等待回答后再推进；不要一次倾倒所有检查问题。
- **局部修改／润色**：只改授权范围，保留其他已确认内容，不借机重新选题。
- **定稿／双语输出**：保留论证、编号、承诺程度和证据边界，再处理语言和页数。

任务粒度由本轮请求决定。用户说“第一页先不动”“只改一句”“整体认可”，即记录为编辑范围，不循环重开已决定问题。

## 2. 材料与证据纪律

### 2.1 确认当前底稿

先读取用户指定文件；存在多版时，以本轮指定版本和最近明确确认版本为编辑依据。旧 proposal、技术计划和过往讨论只补充来源，不自动覆盖新决定。

建立简短的任务记录：用途、读者、语言、正文页数、参考文献规则、输入与输出、时间资源、已确认段落、待决问题。已有材料能解决的，不再询问用户。

**编辑优先级不等于事实真伪优先级。**已确认的措辞若有证据风险，应单独指出并提出最小修改，不把“作者确认”当作外部事实证明。

### 2.2 区分四种陈述

1. 来源明确支持的已有事实或已完成结果。
2. 作者提出、仍待验证的解释或科学假设。
3. 拟采用的工程方案、阈值和实现选择。
4. 有待后续实验支持的潜在应用或延伸价值。

不要把 2—4 写成 1。demo 只证明其实际展示的探索，不自动证明定量优势、机制成立或下游性能提升。

### 2.3 只在需要时扩展检索

纯润色、翻译、基于给定材料总结，不主动重做领域调研。审查可以标记“稿件尚未提供证据”，但不能因此断言领域不存在证据。

用户要求核实文献、更新 SOTA，或确需新增外部事实时，使用可用检索工具核对原论文／官方来源；区分用户材料、独立核验和推断。对具体方法、实验设置与数字，不以二手总结替代原文。表格和图示需实际读取。

无依据时保留待核实项或缩小主张；不编造引用，不将旧范例参考文献当成最新事实。来源相互冲突时明确列出，不默默选择更符合稿件的一方。

## 3. 建立并检验论证链

固定检查顺序：

**应用价值 → 任务与质量要求 → 已有进展 → 具体尚待解决的决策 → 原因假设／科学问题 → 对应方法 → 判别实验 → 成果与适用范围。**

对每个箭头写一句连接句，注明支持类型：应用要求、来源证据、推理、待检验假设。出现“因此”不算完成推导。

### 3.1 背景先讲目标及必要性

先回答“用户希望得到什么成果、用于什么”，再解释为何质量、成本、规模等成为目标的一部分。不要从“本项目决定采用某网络／工具”倒推需求；规模化重要不等于现有方法都不能用。

任务范围用正向描述表达：输入、场景、输出。研究不涉及的技术边界可进入审查记录；正文除非必要，不堆砌“本项目不研究……”说明。

### 3.2 技术选择要有依据，但不必证明唯一性

回答该技术为什么适合当前输出与研究变量，并承认替代路线。区分任务、表示、系统、工具和应用，不制造不处于同一层次的假二选一。

只有声称跨技术路线最优，才承担相应跨路线比较；不能用仅在某一类方法内的优势替代普适结论。

### 3.3 文献先承认成果，再综合局限

按研究目标中的关键维度组织文献，而不是按阅读顺序列论文。本案例的三个维度是规模、几何与质量、训练成本；换课题时重新选择维度。

每类说明“解决什么—如何处理—来源支持了什么”。三类是分析维度，不默认它们共用同一分块、传感器或训练框架。

最后综合各类进展指出一个具体待研究决策。不能从一篇论文的参数局限推出全领域空白，也不能把“没有组合我的模块”当成科学 Gap。

### 3.4 两座桥必须成立

- **进展到问题**：已有证据解决到哪里？在什么输入、质量或资源条件下，仍缺哪项判断依据？
- **问题到方法**：为什么拟改变的因素可能影响目标误差或成本？预期哪种结果支持这一解释，哪种结果使它不成立？

如果只能说“前人没做，所以我来做”，先修这两座桥，不继续润色全文。

### 3.5 科学问题不是模块名称

优先用“专业问题名＋直白问句＋拟揭示的关系／条件”的形式。问题数量服从篇幅和任务，不为凑数拆分。

本案例两问具有依赖：**先判断达到目标质量需要怎样的输入与表示，再研究怎样利用先验以更低成本实现该表示。**

“研究机制”需要变量、响应、竞争解释、干预和适用条件；完整系统优于基线，不足以单独证明某个机制。数学表达仅在确实帮助界定变量、约束和目标时使用，不以最优化符号替代创新依据。

## 4. 方法必须逐项回答问题

每项方法都要能填满这五格：

**目的／对应问题 → 必要性 → 拟采取的操作 → 可观察的产出 → 下一步如何利用／怎样检验。**

案例中的连接句可以直接学习其功能：

> 第一项让影响因素能够被区分；第二项回答“需要怎样的输入与表示”；第三项回答“怎样利用先验减少实现该表示的优化成本”。

不要对所有课题强套这三项。对“机制驱动算法”型计划，要特别检查中间是否真的产生可执行规则，而不只是做出统计图后另拼一套训练技巧。

工具是服务于证据的：例如仿真之所以必要，是为独立控制现实中难以分离的因素。VLM、Blender、实验服务器及编程助手不因被采用就构成创新。

正文写目的、依据、大致操作、产出和关键验证；未知阈值、完整损失清单、实现排错与所有反例留在技术附件或审查记录。需要写清的核心证据边界不能一并删掉。

## 5. 严查“问题—方法—结果”是否换了目标

始终使用引出问题时承诺改善的终点：效率问题不能只用更贵训练下的更高精度作答；泛化不能只看训练拟合；数据效率不能用未披露的额外数据；规模化不能只靠一个局部演示。

每个主张对应一个公平对照、一个可测输出和一个否定／缩小结论的条件。匹配什么由比较目的决定，不机械要求所有实验永远同数量。

若目标是保持质量的加速，考察达到同一预定质量所需的总成本，包含新增处理与训练；可复用拟合和数据制作成本分别披露。更少参数、更少迭代或更低学习率不是实测总成本的替代品。

关联规则在开发数据中确定，在独立数据检验；避免把训练输入当成唯一独立真值。合成真值仅属于构建场景，不默认为原实景完整真值。

## 6. 正式正文与审查记录分开

正式文本：专业、直白、紧凑；先说关系，再给必要技术名词；避免“赋能、颠覆、从根本上解决、填补空白”等无法兑现的修饰。

审查记录：保留替代解释、边界、失败条件、引用核查、实验公平性和未决问题。不要把每一条防误读说明都塞进两页正文。

但不能为了简洁删除维持结论有效的核心信息：目标质量、实际成本口径、独立验证与假设身份应在适当位置保留。

## 7. 推荐输出结构

### 讨论／梳理

输出一条主张、必要的逻辑连接，以及当前最影响全文的一处问题；需要作者判断时只问一个关键问题。

### 完整 review

先给总体诊断，不做虚假的论文命中率预测。最多展开三个首要缺陷，每项采用：

**原句／位置 → 逻辑断点 → 为什么影响主张 → 应有证据 → 最小修订或关键追问。**

区分“逻辑断裂”“原稿缺证据”“科学上待验证”“仅表达可改”，不能因为结果尚未完成就否定 proposal。

### 正式两页稿

遵循接收方要求。本案例默认：

- 第一页：背景与目标；分组现状和综合 Gap；两个相互连接的科学问题。
- 第二页：方法间逻辑开场；三项方法；访问安排、实验条件、初步探索与预期成果。
- 参考文献另页且不计正文页数。验证要点嵌入方法和安排，不擅自恢复作者已删除的独立验证章节。

此结构是本案例的确认版；其他项目按其要求调整。

## 8. 独立评审与交付真实性

只有实际调用了可隔离的委派工具，才可称“独立子 agent 审查”；不得编造指定模型、思考等级、调用结果或身份。

独立 reviewer 先看正文和接收要求，不读取作者的辩护和预设正确答案；写作检查可由另一步核对已确认偏好。没有隔离工具时明确称“当前会话中的评审式自检”，继续完成任务。

输出文件前读取环境适用的文档／PDF技能并渲染验收。不能只凭字数宣称正文正好两页；双语两版分别检查。确认附件存在、链接有依据，视频引用不等于已嵌入视频。

只写实际完成的状态：创建文件不等于已安装技能，结构校验不等于科研结论或独立模型评测通过。

## 9. 发出前的终检

确认以下五点：

1. 需求能够推出目标，目标能支持技术选择，但不虚称唯一性。
2. 文献进展被公平承认，Gap 是有边界的问题，而不是全领域否定。
3. 问题对应可检验关系，方法对应关系中的变量，实验对应最初主张。
4. 原稿已知、提议、推断与潜在应用没有互换；未决事项没有被编造成确定实现。
5. 仅修改授权范围，双语力度一致，删除的段落没有复活，交付状态与实际一致。

## 10. 后续更新

仅在用户提出并确认新的写作偏好／反例时更新本 skill：记录“反馈—规则—适用范围—回归用例”，保留版本和 CHANGELOG。不要把一次稿件的局部选择提升为普遍真理，不擅自改全局配置或覆盖用户文件。
